# 決策紀錄

> 每一條寫：**決定了什麼、為什麼、什麼時候應該推翻它**。
> 最後一欄是重點 —— 沒有寫推翻條件的決策，會變成沒有人敢動的教條。

---

### D1 — 零相依、純靜態

**決定**：不用框架、不用建置工具、不用 npm 相依。
**為什麼**：這東西要在 2027 年還打得開。沒有相依就沒有會過期的相依。Playwright 只在手動 smoke 用，不是專案相依。
**推翻條件**：做了 B（後端）之後，如果前端複雜到手寫 DOM 開始出錯。**現在還沒到。**

---

### D2 — 行程資料與程式分離

**決定**：`trip.js` 裝內容，`app.js` 一個日期／班號／地名／金額都不能有。
**為什麼**：這是「第二趟旅行」的前提條件。
**怎麼守**：`scripts/fixtures/sample.trip.js` 是一份完全不同的旅行（東京、日圓、2 人、UTC+9），smoke 會用它整個跑一次。**這條規則有自動化的看門狗，不是靠自律。**
**推翻條件**：無。這是地基。

---

### D3 — 不做後端（暫時）

**決定**：沒有伺服器、沒有帳號、沒有同步。
**為什麼**：共同的東西已經靠部署同步了。為了「現場改內容」這一個需求養一個服務，是為了簡單需求過度工程。
**代價**：帶隊的人在 app 裡寫的東西只存在自己手機上。
**推翻條件**：見 `architecture.md` B 段那四個條件。

---

### D4 — 跟隊模式的狀態由時鐘推導

**決定**：不需要有人按「我們出發了」。
**為什麼**：**在沒有後端的前提下，這題其實沒得選** —— 帶隊的人按了，那一下也傳不到其他四支手機上。與其做一個只對自己有效的按鈕，不如誠實地讓時鐘決定。
**代價**：延誤的時候畫面會說謊。
**推翻條件**：做了 B 之後立刻重新考慮。那時「帶隊的人按一下、所有人的畫面跟著變」才真的成立。

---

### D5 — 12 字、4 步，硬限制

**決定**：一句話 ≤ 12 字，步驟 ≤ 4 步，在 `check-trip.mjs` 和編輯器裡都擋。
**為什麼**：超過就不是口令了。而且中文沒有空格，長句會斷在詞中間。
**注意**：欄位的 `maxlength` 不算數 —— 程式裡要再擋一次，不然繞過 UI 就破功（smoke 有測這個）。
**推翻條件**：無，除非使用者測試證明人真的記得住更多。**接 AI 之後這條更重要**，模型很愛超過。

---

### D6 — 個人／共同用「放哪裡」區分，不用每項一個開關

**決定**：共同的放 `trip.js`（跟著部署），個人的放 localStorage。新增待辦時選的是「加到哪個清單」，不是「這項要不要分享」。
**為什麼**：一次決定 vs. 每項永遠都要決定一次。
**推翻條件**：無。這個模式在 B 之後仍然成立。

---

### D7 — 勾選狀態 key 在 id 上，不在陣列位置

**決定**：每則待辦要有唯一 `id`，勾選存在 id 上。
**為什麼**：原本 key 在陣列位置，**在 `trip.js` 最上面插一則待辦，會把所有人已經勾好的狀態默默移到錯的項目上**。清單從來沒改過所以從來沒發作；而「新增待辦」正是會讓它發作的功能。
**教訓**：這類 bug 不會在測試裡出現，因為測試也用同一份沒動過的資料。**發出去的 id 就不要再改。**
**推翻條件**：無。

---

### D8 — `[hidden]{display:none!important}`

**決定**：全域一條規則，蓋過所有作者自訂的 `display`。
**為什麼**：「自己寫的 `display` 規則蓋過 `hidden` 屬性」這個 bug **出貨過三次**：每日規劃空狀態蓋在真行程上、關閉的對話框吃掉點擊、跟隊模式的幽靈航段條。
**怎麼守**：smoke 會走過每個 view 裡每個帶 `hidden` 的元素，斷言它真的沒被畫出來。
**推翻條件**：無。

---

### D9 — 只有亮色和深色兩種主題

**決定**：拿掉「跟隨系統」這個第三狀態。
**為什麼**：三個狀態的切換器沒有人看得懂自己現在在哪一個。沒選過的時候仍然預設跟隨系統，只是不佔一個按鈕。
**深色模式的規則**：亮度**往上疊** —— 頁面 < 卡片 < 卡片裡的小塊。不要用「把亮色反過來」的方式做，那會讓最重要的元素變成最暗的。
**推翻條件**：無。

---

### D10 — 手動的 smoke 不進 CI

**決定**：`check-tokens.mjs` 和 `check-trip.mjs` 進 CI；`smoke.mjs` 不進。
**為什麼**：smoke 需要 Playwright + Chromium，進 CI 就等於引入相依，違反 D1。
**代價**：要靠人記得跑。**改完 `app.js` 或 `styles.css` 一定要跑。**
**推翻條件**：如果忘記跑導致出貨 bug 超過兩次，就該重新權衡 D1。

---

### D11 — 預覽時間一定要標示在畫面上

**決定**：`?at=` 和「看跟隊畫面」都會在畫面頂端顯示「預覽模式」。
**為什麼**：一個看起來像真的預覽，比沒有預覽更危險 —— 有人會照著一個不是現在的畫面行動。
**推翻條件**：無。

---

### D12 — 出發前不要用「沒有要趕的事」

**決定**：旅行開始前顯示「出發前／還有 N 天」，不跟旅行中的空檔日共用同一句話。
**為什麼**：實際被回報成 bug。**正確地安靜和壞掉，在畫面上長得一模一樣。**
**通則**：**任何「什麼都不用做」的狀態，都要說清楚是哪一種什麼都不用做。**
**推翻條件**：無。

---

### D13 — AI 生成先做「複製貼上」，不先接 API

**決定**：app 產生 prompt，人帶去 Claude，把 JSON 貼回來。**不打 API、不存金鑰、不送任何東西出去。**
**為什麼**：接 API 之前要先知道**生成品質夠不夠**。如果不夠，一整套金鑰架構就是白做的。這個版本花的力氣是那個版本的十分之一，但回答同一個問題。
**附帶好處**：使用者用自己已經在付的 Claude 訂閱，沒有多一筆費用、沒有金鑰暴露、repo 公開也無所謂。
**推翻條件**：品質確認夠好，而且複製貼上的次數多到變成負擔。那時看 `architecture.md` A 段的取捨表 —— 注意 BYOK 只在「只有自己用」時可接受。

---

### D14 — 模型寫的東西要過跟人一樣的閘門

**決定**：貼回來的 JSON 走 `checkDraft()`，違規的**整筆不套用**並說出原因，不截斷、不修正。
**為什麼**：模型很愛超過 12 字。**如果對模型放寬，那個限制就等於不存在了** —— 而那是整個畫面能一眼讀完的唯一理由。
**注意**：不要「幫它截短到 12 字」。截斷會產生一句沒人寫過、也沒人檢查過的話，那比拒絕更糟。
**推翻條件**：無。

---

### D15 — AI 起草的內容要標記，而且只有人讀過才會消失

**決定**：套用進來的內容標成 `by:'ai'`，行程列上顯示「AI 起草，還沒有人檢查」。**只有人打開編輯器按下儲存，標記才會變成 `me`。**
**為什麼**：這些字是要給人在機場照著做的。**沒有人檢查過的內容和有人檢查過的內容，不能長得一樣。**
**為什麼是「儲存」而不是「打開」**：打開不代表讀過。按下儲存代表每一個欄位都在眼前出現過。
**推翻條件**：無。這個規則在接了 API 之後更重要，不是更不重要。
